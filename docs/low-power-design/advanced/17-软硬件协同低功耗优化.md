# 第17章 软硬件协同低功耗优化

## 17.1 引言

真正的低功耗系统优化不是硬件或软件单独能完成的——**软硬件协同优化**才能挖掘出最大的功耗节省潜力。编译器可以在代码生成阶段减少不必要的活动；算法设计可以从根本上减少计算量；硬件感知的软件设计可以充分利用芯片的低功耗特性。本章从编译器优化、算法级优化和系统级协同三个层面介绍软硬件协同低功耗设计方法。

## 17.2 编译器级功耗优化

### 17.2.1 编译器如何影响功耗

```
编译器对功耗的影响路径:

源代码 → 编译器优化 → 机器码 → 执行 → 功耗

编译器影响功耗的方式:
  1. 指令数量: 更少指令 → 更少动态功耗
  2. 指令类型: 避免高功耗指令(乘法/除法/浮点)
  3. 内存访问: 减少缓存miss → 减少DRAM访问功耗
  4. 分支预测: 减少误预测 → 减少流水线冲刷功耗
  5. 数据布局: 提高局部性 → 降低缓存功耗
  6. 信号翻转: 减少总线翻转 → 降低互连功耗
```

### 17.2.2 GCC/LLVM 功耗相关优化选项

```
编译器功耗优化选项:

# GCC 功耗相关优化
gcc -Os            # 优化代码大小 (减少指令缓存miss)
gcc -O2            # 标准优化 (减少指令数)
gcc -ffunction-sections -fdata-sections  # 死代码消除
gcc -flto          # 链接时优化 (跨文件优化)

# ARM 特定低功耗选项
gcc -mcpu=cortex-a55    # 针对小核优化
gcc -mfloat-abi=hard    # 硬件浮点 (避免软件模拟)
gcc -mfpu=neon-vfpv4    # 使用SIMD减少循环次数

# LLVM/Clang
clang -Oz          # 极致大小优化
clang -mllvm -polly # 多面体优化 (循环优化)

优化级别对功耗的影响:
┌────────┬──────────────┬───────────┬──────────────┐
│ 级别   │ 代码大小     │ 执行时间  │ 相对功耗     │
├────────┼──────────────┼───────────┼──────────────┤
│ -O0    │ 最大         │ 最慢      │ 100% (基准)  │
│ -O1    │ 大           │ 较快      │ ~75%         │
│ -O2    │ 中等         │ 快        │ ~60%         │
│ -O3    │ 较大(展开)   │ 最快      │ ~55%         │
│ -Os    │ 最小         │ 较快      │ ~58%         │
└────────┴──────────────┴───────────┴──────────────┘

注意: -O3不一定最低功耗!
  循环展开增加代码大小 → I-Cache miss增加 → 功耗可能增加
  -Os or -O2 往往在功耗方面最优
```

### 17.2.3 数据布局优化

```
数据布局对缓存命中率的影响:

AoS (Array of Structures) - 缓存不友好:
struct Particle {
    float x, y, z;       // 位置
    float vx, vy, vz;    // 速度
    float mass;           // 质量
    float charge;         // 电荷
};
struct Particle particles[10000];
// 遍历所有x: 每次加载整个结构，浪费缓存

SoA (Structure of Arrays) - 缓存友好:
struct Particles {
    float x[10000];
    float y[10000];
    float z[10000];
    float vx[10000];
    // ...
};
// 遍历所有x: 连续内存访问，缓存命中率高

功耗影响:
  AoS: L1 miss率 ~40% → 频繁访问L2/L3/DRAM
  SoA: L1 miss率 ~5%  → 主要在L1完成
  功耗差异: SoA 可以节省 20-40% 内存相关功耗
```

## 17.3 算法级功耗感知设计

### 17.3.1 计算复杂度与功耗

```
算法选择对功耗的影响:

同样的排序任务 (100万数据):

算法           复杂度         操作次数       相对功耗
──────────────────────────────────────────────────────
冒泡排序       O(n²)         ~10¹²          1000×
快速排序       O(n log n)    ~2×10⁷         20×
计数排序       O(n+k)        ~2×10⁶         2×
硬件加速排序   O(n)          ~10⁶           1×

关键原则:
  1. 更低复杂度的算法 → 更少运算 → 更低功耗
  2. 减少内存访问的算法 → 更低数据搬运功耗
  3. 利用硬件加速的算法 → 更高能效
```

### 17.3.3 信号处理低功耗算法

```
信号处理中的功耗感知算法选择:

FFT vs 直接卷积:
  直接卷积: O(N²) → N大时功耗高
  FFT卷积:  O(N log N) → N大时更省
  但FFT需要浮点 → 小N时直接卷积用整数更省

定点 vs 浮点:
  浮点: 高精度, 高功耗 (FPU)
  定点: 适当精度, 低功耗 (仅ALU)
  策略: 分析精度需求, 尽可能用定点

事件驱动 vs 连续采样:
  连续采样: 固定速率采集 → 恒定功耗
  事件驱动: 有信号才采集 → 平均功耗低得多
  
  示例: 声音检测
  连续: 16kHz × 16bit = 256kbps → 持续ADC+处理
  事件: 硬件检测器触发 → 99%时间关断 → ~100×节省
```

## 17.4 硬件感知软件设计

### 17.4.1 利用硬件低功耗特性

```
软件如何利用硬件低功耗特性:

1. 利用时钟门控
   ├── 软件端: 完成操作后释放设备
   ├── 硬件端: 自动门控未使用模块的时钟
   └── 示例: DMA传输完成后释放DMA控制器

2. 利用电源域
   ├── 软件端: 不需要GPU时告知PM框架
   ├── 硬件端: PM域自动关断GPU电源
   └── 关键: 避免频繁开关 (有开关延迟和能量开销)

3. 利用DVFS
   ├── 软件端: 告知调度器当前负载
   ├── 硬件端: 调节电压和频率
   └── 关键: 避免频率振荡 (频繁升降)

4. 利用Cache
   ├── 软件端: 优化数据访问模式提高命中率
   ├── 硬件端: Cache命中→不访问DRAM
   └── DRAM访问功耗是Cache的 100× 以上
```

### 17.4.2 功耗感知任务调度

```
功耗感知任务调度策略:

策略1: Race-to-Idle
  ├── 思路: 以最高频率快速完成任务, 然后进入深度睡眠
  ├── 优势: 总能量可能更低 (漏电时间短)
  └── 适用: 短burst任务, 深度睡眠功耗很低的系统

策略2: Pace-to-Deadline
  ├── 思路: 以恰好满足Deadline的最低频率运行
  ├── 优势: 动态功耗 ∝ V²f, 低电压极大降低功耗
  └── 适用: 有明确Deadline的实时任务

策略3: Batch Processing
  ├── 思路: 积累多个任务一起处理
  ├── 优势: 减少唤醒次数, 延长深度睡眠时间
  └── 适用: 非实时任务 (传感器数据上传等)

能量对比 (处理100个数据包):
  逐个处理: 100 × (唤醒能量 + 处理能量 + 睡眠过渡)
  批量处理: 1 × (唤醒能量 + 100 × 处理能量 + 睡眠过渡)
  节省: 99 × (唤醒能量 + 睡眠过渡) ← 可节省 30-50%
```

## 17.5 通信协议功耗优化

### 17.5.1 协议选择

```
无线协议功耗对比:

协议      峰值功耗   平均功耗(典型)  速率       范围
────────────────────────────────────────────────────
BLE 5.0   15 mW     0.1-1 mW      2 Mbps     ~100m
WiFi      600 mW    20-50 mW      100 Mbps   ~100m
Zigbee    50 mW     0.5-2 mW      250 kbps   ~100m
LoRa      400 mW    0.01-0.1 mW   50 kbps    ~10km
NB-IoT    200 mW    1-5 mW        200 kbps   ~10km
LTE Cat-M 200 mW    2-10 mW       1 Mbps     ~10km

选择原则:
  近距离 + 低速率 → BLE (功耗最低)
  近距离 + 高速率 → WiFi (带宽充足时短暂连接)
  远距离 + 低速率 → LoRa (覆盖范围大, 功耗极低)
```

### 17.5.2 通信功耗优化技巧

```
通信功耗优化策略:

1. 数据压缩
   ├── 原始数据: 1000 bytes @ 10 pJ/bit = 80 nJ
   ├── 压缩后:   200 bytes @ 10 pJ/bit = 16 nJ
   ├── 压缩能耗:  ~5 nJ (CPU处理)
   └── 净节省: 80 - 16 - 5 = 59 nJ (74%!)
   
   前提: 压缩能耗 < 节省的传输能耗

2. 差分传输
   ├── 不传完整数据, 只传变化量
   ├── 传感器数据变化通常 < 10%
   └── 可减少 50-90% 传输量

3. 自适应采样率
   ├── 信号变化大 → 高采样率
   ├── 信号稳定   → 低采样率
   └── 动态调节可减少 50-80% 数据量

4. 连接参数优化
   ├── 根据实际需求调整连接间隔
   ├── 使用Slave Latency跳过空闲事件
   └── 数据传完立即进入低功耗
```

## 17.6 传感器融合与功耗

### 17.6.1 传感器轮转策略

```
传感器轮转 (Sensor Batching):

传统方式: 每次采样都唤醒AP处理
  唤醒AP(10mW) × 100次/秒 = 频繁唤醒

Sensor Hub方式:
  ┌────────────────────────────────────┐
  │  Sensor Hub (低功耗协处理器)        │
  │  ├── 收集传感器数据 (~10μW)        │
  │  ├── 本地缓冲 (FIFO)              │
  │  ├── 简单处理 (计步/手势检测)       │
  │  └── 批量传给AP (减少唤醒)          │
  └────────────────────────────────────┘

功耗对比:
  无Sensor Hub: AP频繁唤醒 → 平均 ~5 mW
  有Sensor Hub: AP每5秒唤醒一次 → 平均 ~0.5 mW
  节省: ~90%
```

## 17.7 系统级协同优化案例

### 17.7.1 智能手表协同优化

```
智能手表软硬件协同优化:

硬件特性:
  ├── 双核: Cortex-M4 (低功耗) + Cortex-A35 (高性能)
  ├── 专用Sensor Hub
  ├── ePaper/AMOLED 显示
  └── BLE 5.0

软件策略:
  ┌─────────────────────────────────────────────┐
  │ 场景: 日常佩戴 (99% 时间)                    │
  │ 活跃核: M4 only                              │
  │ 功能: 计步, 心率, 时间显示                    │
  │ 功耗: ~2 mW                                  │
  ├─────────────────────────────────────────────┤
  │ 场景: 通知/消息查看 (偶尔)                    │
  │ 活跃核: M4 + A35                              │
  │ 功能: 显示通知, BLE同步                       │
  │ 功耗: ~50 mW (持续 ~5秒)                      │
  ├─────────────────────────────────────────────┤
  │ 场景: GPS运动追踪                             │
  │ 活跃核: M4 + A35 + GPS                        │
  │ 功能: 持续定位, 运动分析                       │
  │ 功耗: ~100 mW                                 │
  └─────────────────────────────────────────────┘

平均功耗 (日常使用):
  2mW × 98% + 50mW × 1.5% + 100mW × 0.5%
  = 1.96 + 0.75 + 0.5 = 3.21 mW
  
  300mAh 电池 @ 3.7V = 1110 mWh
  续航: 1110 / 3.21 ≈ 345 小时 ≈ 14.4 天
```

## 17.8 功耗Profile与优化工具

### 17.8.1 软件功耗Profile方法

```
功耗Profile方法:

1. 硬件测量
   ├── 电流探头 + 示波器 → 实时波形

3. 联合分析
   ├── 硬件波形 + 软件时间戳 → 关联分析
   ├── 识别高功耗软件行为
   └── 定向优化
```
