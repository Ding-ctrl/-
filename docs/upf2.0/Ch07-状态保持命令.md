# Ch07 - 状态保持命令

## 概述

当一个电源域关断后，域内所有寄存器的值会丢失。如果希望在**重新上电后恢复到关断前的状态**（避免完全重新初始化），就需要使用**状态保持 (Retention)** 技术。UPF 中的 `set_retention` 命令描述了哪些寄存器需要保持状态以及如何保持。

---

## 7.1 为什么需要状态保持？

### 没有 Retention 的场景

```
时间线:  T1(运行)    T2(关断)    T3(重新上电)
         
  CPU 寄存器:  R0=0x1234    R0=XXXX     R0=0x0000 (重置)
  状态机:      STATE_RUN    STATE_XX    STATE_IDLE (重置)
  配置寄存器:  CFG=0xABCD   CFG=XXXX    CFG=0x0000 (重置)
  
  → 重新上电后，软件需要完全重新初始化
  → 恢复时间长，功耗浪费大
  → 用户体验差（如手机从深度睡眠唤醒慢）
```

### 有 Retention 的场景

```
时间线:  T1(运行)    T2(关断)    T3(重新上电)
         
  CPU 寄存器:  R0=0x1234    [保存]      R0=0x1234 ← 恢复！
  状态机:      STATE_RUN    [保存]      STATE_RUN ← 恢复！
  配置寄存器:  CFG=0xABCD   [保存]      CFG=0xABCD ← 恢复！
  
  → 重新上电后，从中断点恢复执行
  → 恢复时间短（微秒级 vs 毫秒级）
  → 用户体验好（快速唤醒）
```

## 7.2 set_retention

### 命令语法

```tcl
set_retention retention_name
    -domain domain_name
    [-elements {element_list}]
    [-retention_power_net net_name]
    [-retention_ground_net net_name]
    [-retention_supply_set supply_set_name]
    [-save_signal {signal_name edge}]
    [-restore_signal {signal_name edge}]
    [-retention_condition {boolean_expr}]
    [-no_retention]
    [-use_retention_as_primary]
```

### 参数详解

| 参数 | 含义 | 芯片上的影响 |
|------|------|------------|
| `-domain` | 应用保持的域 | 该域内的 FF 替换为 Retention FF |
| `-elements` | 指定元素 | 精确控制哪些 FF 需要 Retention |
| `-retention_power_net` | 保持电路的供电 | 必须是常开电源 (Always-On VDD) |
| `-retention_ground_net` | 保持电路的接地 | 通常是全局 VSS |
| `-save_signal` | 保存触发信号 | 关断前触发数据保存到 Balloon Latch |
| `-restore_signal` | 恢复触发信号 | 上电后触发数据从 Balloon Latch 恢复 |
| `-retention_condition` | 保持条件 | 满足条件时才执行保持（可选） |
| `-no_retention` | 免除保持 | 指定的 FF 不需要 Retention |

### 对实际芯片的作用

#### 7.2.1 Retention FF 的电路结构

```
标准 FF (无 Retention)：
                    VDD_SW (可切断)
                     │
  ┌──────────────────┴────────────────┐
  │            Standard FF            │
  │  D ──→ [Master Latch] ──→ [Slave │
  │  CLK──→                   Latch] ──→ Q
  │                                   │
  └──────────────────┬────────────────┘
                     │
                    VSS
  
  断电后：所有内部节点放电 → 数据丢失！


Retention FF (带 Balloon Latch)：

                VDD_SW (可切断)        VDD_RET (常开)
                 │                      │
  ┌──────────────┴──────────┐  ┌───────┴───────┐
  │      Standard FF 部分    │  │ Balloon Latch │
  │                          │  │   (Always-On) │
  │  D→[Master]→[Slave]→Q   │  │               │
  │       │          │       │  │  ┌─────────┐  │
  │       │          └───────┼──┼──┤ Shadow  │  │
  │       │    SAVE ─────────┼──┼──┤ Latch   │  │
  │       │                  │  │  └────┬────┘  │
  │       │    RESTORE ──────┼──┼───────┘       │
  │       │          ┌───────┼──┼───────────────│
  │       │          │       │  │               │
  └──────────────────┘───────┘  └───────────────┘
                 │                      │
                VSS                    VSS

  工作流程：
  1. SAVE 信号触发 → 主 FF 数据复制到 Balloon Latch
  2. 主域断电 → 主 FF 数据丢失，但 Balloon Latch 保持
  3. 主域上电 → RESTORE 信号触发 → 数据从 Balloon 恢复到主 FF
```

#### 7.2.2 两种 Retention FF 架构

```
架构 1: Balloon Latch (最常见)

  ┌──────────── VDD_SW ────────────────────── VDD_RET ───┐
  │                                                       │
  │  ┌──────────────────┐      ┌──────────────────┐      │
  │  │   Main FF        │ SAVE │   Balloon Latch  │      │
  │  │  ┌──┐   ┌──┐    │──→──│  ┌──────────┐    │      │
  │  │  │M │──→│S │──Q │      │  │Shadow FF │──→─│──Q_ret│
  │  │  └──┘   └──┘    │←──←──│  └──────────┘    │      │
  │  │   D    CLK       │RESTORE   Always-On      │      │
  │  └──────────────────┘      └──────────────────┘      │
  │                                                       │
  面积开销: +30~50% (相比标准 FF)
  功耗开销: Balloon Latch 有持续漏电


架构 2: Master-Slave with Retention (MSFR)

  ┌────────────────── VDD_SW ──────────────── VDD_RET ───┐
  │                                                       │
  │  ┌─────────────────────────────────────────────────┐  │
  │  │  Master (VDD_SW)  │ Slave (VDD_RET, Always-On) │  │
  │  │  ┌──────────┐     │  ┌──────────┐              │  │
  │  │  │ Normal   │     │  │ Retention│              │  │
  │  │  │ Master   │────→│  │ Slave    │──→ Q         │  │
  │  │  │ Latch    │     │  │ Latch    │              │  │
  │  │  └──────────┘     │  └──────────┘              │  │
  │  └─────────────────────────────────────────────────┘  │
  │                                                       │
  面积开销: +15~25% (比 Balloon Latch 小)
  注意: Slave 本身就是 always-on，不需要额外 save/restore
```

#### 7.2.3 Save/Restore 时序

```
完整的 Power-Down / Power-Up 序列中的 Retention 时序：

═══ 关断序列 (Power-Down) ═══

  clk_enable  ──┐
                └──────────────────────────  (1) 先停时钟

  save        ─────┌───┐
                   │   └──────────────────  (2) 触发保存
                   ↑
              Main FF 数据 → Shadow Latch

  iso_enable  ──────────┌─────────────────  (3) 开启隔离

  power_sw    ───────────────┐
                             └────────────  (4) 最后断电

═══ 唤醒序列 (Power-Up) ═══

  power_sw    ──────┌─────────────────────  (1) 先上电
                    │
  power_ack   ──────────┌─────────────────  (2) 电源稳定确认

  restore     ──────────────┌───┐
                            │   └─────────  (3) 触发恢复
                            ↑
              Shadow Latch 数据 → Main FF

  iso_enable  ─────────────────────┐
                                   └──────  (4) 关闭隔离

  clk_enable  ────────────────────────┌───  (5) 最后恢复时钟
                                      │
                                  从断点继续执行
```

### 使用示例

```tcl
# 示例 1: CPU 域所有寄存器保持状态
set_retention ret_cpu \
    -domain PD_CPU \
    -retention_power_net VDD \
    -retention_ground_net VSS \
    -save_signal    {cpu_save    high} \
    -restore_signal {cpu_restore high}

# 示例 2: 仅保持关键寄存器（减少面积开销）
set_retention ret_cpu_critical \
    -domain PD_CPU \
    -elements {u_cpu/u_regfile u_cpu/u_state_machine u_cpu/u_config_regs} \
    -retention_power_net VDD \
    -retention_ground_net VSS \
    -save_signal    {cpu_save    posedge} \
    -restore_signal {cpu_restore posedge}

# 示例 3: 免除不需要保持的寄存器
set_retention ret_cpu_no \
    -domain PD_CPU \
    -elements {u_cpu/u_debug_regs u_cpu/u_perf_counters} \
    -no_retention
# 调试寄存器和性能计数器不需要保持 → 节省面积
```

## 7.3 Retention 的面积和功耗开销

### 面积开销对比

```
标准 FF 面积 = 1x (基准)

┌──────────────────┬───────────┬──────────────────────┐
│ FF 类型           │ 面积 (相对)│ 说明                  │
├──────────────────┼───────────┼──────────────────────┤
│ 标准 FF           │ 1.0x      │ 基准                  │
│ Retention FF     │ 1.3~1.5x  │ +Balloon Latch        │
│ (Balloon)        │           │                       │
│ Retention FF     │ 1.15~1.25x│ Slave 本身 Always-On  │
│ (MSFR)           │           │                       │
│ Retention FF     │ 1.4~1.6x  │ +Balloon +Level Shift │
│ (跨电压域)        │           │                       │
└──────────────────┴───────────┴──────────────────────┘
```

### 功耗开销

```
┌──────────────────┬───────────────────────────────────┐
│ 状态              │ 功耗影响                           │
├──────────────────┼───────────────────────────────────┤
│ 正常工作 (Active) │ Retention FF 比标准 FF 多 ~5-10%  │
│                   │ 延迟（因为 Balloon 负载）           │
│ 关断状态 (Sleep)  │ Balloon Latch 持续漏电 ~0.1-1μW   │
│                   │ 但远小于整个域的运行功耗            │
│ Save 操作         │ 短暂脉冲功耗 ~1 clock cycle       │
│ Restore 操作      │ 短暂脉冲功耗 ~1 clock cycle       │
└──────────────────┴───────────────────────────────────┘
```

## 7.4 Always-On 逻辑

### 概念

在可关断域内，有些逻辑需要**始终保持通电**（如唤醒检测逻辑）。这些逻辑虽然物理上位于可关断域的区域内，但由常开电源供电。

```
PD_CPU (可关断域)
┌─────────────────────────────────────────┐
│ VDD_SW_CPU (可切断)                       │
│                                          │
│  ┌───┐  ┌───┐  ┌───┐  ┌───┐  ┌───┐     │
│  │FF │  │FF │  │FF │  │FF │  │FF │     │ ← 普通逻辑 (可关断)
│  └───┘  └───┘  └───┘  └───┘  └───┘     │
│                                          │
│  ┌──────────────────────────────┐        │
│  │ Always-On Island             │        │
│  │ VDD (常开)                    │        │
│  │                              │        │
│  │  ┌────────┐  ┌───────────┐  │        │
│  │  │WakeUp  │  │Always-On  │  │        │
│  │  │Detect  │  │Buffer     │  │        │
│  │  └────────┘  └───────────┘  │        │
│  └──────────────────────────────┘        │
│                                          │
└─────────────────────────────────────────┘

Always-On 单元特点：
- 物理上在可关断域区域内
- 电气上连接到常开 VDD
- 使用库中的 Always-On Cell
- 需要 Always-On Buffer 驱动
```

### UPF 描述

```tcl
# 在 PD_CPU 域内声明 Always-On 元素
# 这些元素虽然在 PD_CPU 域的物理区域，但使用常开电源
create_power_domain PD_CPU -elements {u_cpu_subsys}

# Always-On 信号通过常开缓冲器传播
# EDA 工具会自动在可关断域内插入 Always-On Buffer
```

## 7.5 高级 Retention 主题

### 7.5.1 部分 Retention 策略

在实际设计中，通常不需要对域内所有寄存器做 Retention。选择性保持可以大幅降低面积开销：

```
全量 Retention:
  域内 10,000 个 FF → 全部替换为 Retention FF
  面积增加: 10,000 × 40% = +4,000 FF 等效面积
  → 面积开销巨大！

部分 Retention:
  关键寄存器: 500 个 → 替换为 Retention FF
  普通寄存器: 9,500 个 → 保持标准 FF
  面积增加: 500 × 40% = +200 FF 等效面积
  → 面积开销降低 95%！
```

**选择 Retention 的优先级：**

| 优先级 | 寄存器类型 | 数量（典型） | 是否 Retention | 原因 |
|--------|-----------|-------------|:---:|------|
| P0 | CPU 架构寄存器 (PC, SP, LR) | ~30 | ✅ | 恢复执行必需 |
| P0 | 状态机寄存器 | ~50-200 | ✅ | 恢复状态必需 |
| P1 | 配置寄存器 (Control/Config) | ~100-500 | ✅ | 避免重新配置 |
| P2 | 通用寄存器 (Reg File) | ~32-64 | ✅/❌ | 取决于软件恢复成本 |
| P3 | 数据缓存 Tag | ~200-1000 | ❌ | 可以 invalidate |
| P3 | FIFO/Buffer 数据 | ~500-2000 | ❌ | 可以重新填充 |
| P4 | 调试/性能计数器 | ~50-200 | ❌ | 非必需 |

```tcl
# 部分 Retention 的 UPF 描述
# 仅保持关键寄存器
set_retention ret_cpu_critical \
    -domain PD_CPU \
    -elements {u_cpu/u_arch_regs u_cpu/u_fsm u_cpu/u_config} \
    -retention_supply_set SS_ALWAYS_ON \
    -save_signal    {save    high} \
    -restore_signal {restore high}

# 明确排除非关键寄存器
set_retention ret_cpu_exclude \
    -domain PD_CPU \
    -elements {u_cpu/u_debug u_cpu/u_perf_cnt u_cpu/u_cache_data} \
    -no_retention
```

### 7.5.2 软件辅助 vs 硬件 Retention

```
方案一：纯硬件 Retention (Retention FF)

  save信号 → [Balloon Latch 自动保存]
  restore信号 → [Balloon Latch 自动恢复]
  
  优点：恢复速度快（~1 clock cycle），软件无感知
  缺点：面积开销大（每个 FF +30-50%）
  适用：快速唤醒场景（如手机屏幕唤醒）

方案二：软件辅助 Retention (Save to SRAM/DDR)

  软件中断 → [软件读取寄存器值] → [写入 Always-On SRAM]
  → 断电 →
  → 上电 → [软件从 SRAM 读取] → [软件恢复寄存器值]
  
  优点：不需要 Retention FF，面积开销为 0
  缺点：恢复时间长（毫秒级），需要软件支持
  适用：深度睡眠场景（如手机长时间待机）

方案三：混合 Retention

  关键硬件寄存器 → Retention FF（快速恢复）
  大量数据寄存器 → 软件保存到 SRAM（面积优化）
  
  → 在恢复速度和面积之间取得平衡
  → 业界最常用的方案
```

### 7.5.3 Retention 对时序的影响

```
Retention FF 的时序特性：

  ┌─────────────────────────────────────────────────┐
  │ 参数          │ 标准 FF    │ Retention FF │ 差异  │
  ├───────────────┼────────────┼──────────────┼──────┤
  │ Setup time    │ 50 ps      │ 55-65 ps     │ +10% │
  │ Hold time     │ 20 ps      │ 22-25 ps     │ +10% │
  │ Clk-to-Q      │ 80 ps      │ 90-100 ps    │ +15% │
  │ 面积           │ 1.0x       │ 1.3-1.5x     │ +40% │
  │ 漏电流         │ 1.0x       │ 1.1-1.2x     │ +15% │
  └─────────────────────────────────────────────────┘

  影响：
  1. 关键路径上的 Retention FF 会降低最高频率
  2. Save/Restore 操作需要一个完整的时钟周期
  3. 在时序分析中需要使用 Retention FF 的 liberty
  
  优化：
  → 关键路径上尽量使用标准 FF
  → Retention FF 放在非关键路径上
  → 使用 -elements 精确控制
```

### 7.5.4 多域 Retention 的协调

```
当多个域需要 Retention 时，save/restore 的顺序很重要：

  场景：PD_CORE0 和 PD_CORE1 共享 L2 Cache

  关断顺序：
  1. Core0 save → Core0 断电
  2. Core1 save → Core1 断电
  3. L2 可以不断电（保持缓存数据）

  唤醒顺序：
  1. Core0 上电 → Core0 restore
  2. Core1 上电 → Core1 restore
  3. 两个核心恢复执行，L2 数据仍然有效

  注意事项：
  - 各域的 save/restore 信号必须独立
  - PMU 需要管理多域的唤醒顺序
  - 共享资源（如 L2）的电源策略需要单独考虑
```

## 7.6 本章小结

| 要点 | 说明 |
|------|------|
| `set_retention` | 指定需要保持状态的寄存器 → 替换为 Retention FF |
| Balloon Latch | 常开的影子寄存器 → 关断时保持数据 |
| Save/Restore | PMU 控制的保存/恢复信号 → 严格的时序要求 |
| 面积开销 | Retention FF 比标准 FF 大 30-50% → 按需选择 |
| Always-On | 可关断域内的常开逻辑 → 唤醒检测等关键功能 |
| 时序 | 关断先保存再断电，上电先通电再恢复 |
