# 第5章 功能安全与信息安全模块

## 5.1 功能安全概述（ISO 26262）

### 5.1.1 汽车功能安全法规体系

```
功能安全法规层次

  ISO 26262（道路车辆功能安全）
  ├── Part 1：词汇表
  ├── Part 2：功能安全管理
  ├── Part 3：概念阶段（危害分析与风险评估 HARA）
  ├── Part 4：系统层面产品开发
  ├── Part 5：硬件层面产品开发 ◄─ 芯片硬件设计
  ├── Part 6：软件层面产品开发 ◄─ 芯片内部软件
  ├── Part 7：生产、运营与报废
  ├── Part 8：支持过程
  ├── Part 9：汽车安全完整性等级（ASIL）准则
  ├── Part 10：ISO 26262指南
  ├── Part 11：半导体应用
  └── Part 12：摩托车

ASIL等级划分（A < B < C < D，D最高）：
  ├── QM：质量管理，无安全要求
  ├── ASIL-A：最低安全等级
  ├── ASIL-B：中等安全等级（仪表车速显示）
  ├── ASIL-C：较高安全等级
  └── ASIL-D：最高安全等级（转向/制动等）

座舱SoC功能安全等级分配：
  ├── 安全岛（Safety Island）：ASIL-D
  ├── 实时MCU Cluster：ASIL-B
  └── 应用处理器（A核+GPU+NPU）：QM（软件诊断覆盖）
```

### 5.1.2 安全岛（Safety Island）架构

安全岛是座舱SoC内专为功能安全设计的独立子系统，与主处理器在电气上隔离：

```
安全岛内部架构

  ┌──────────────────────────────────────────────────────┐
  │                    安全岛（Safety Island）              │
  │  ASIL-D设计，独立电源域，与主处理器硬件隔离               │
  │                                                      │
  │  ┌─────────────────────┐  ┌──────────────────────┐   │
  │  │   Lockstep MCU对    │  │   安全外设              │   │
  │  │   ┌────┐  ┌────┐   │  │   ├── 安全看门狗(IWDG) │   │
  │  │   │MCU0│  │MCU1│   │  │   ├── 时钟/电压监控    │   │
  │  │   └──┬─┘  └──┬─┘   │  │   ├── CAN-FD安全过滤  │   │
  │  │      └──比较──┘    │  │   └── 安全SRAM(ECC)   │   │
  │  │      差异检测器      │  └──────────────────────┘   │
  │  └─────────────────────┘                              │
  │                                                      │
  │  ┌─────────────────────────────────────────────────┐  │
  │  │   安全通信路径                                    │  │
  │  │   ├── 安全显示控制器（仪表安全信号专用）            │  │
  │  │   ├── 安全帧缓冲区（ECC SRAM保护）                 │  │
  │  │   └── 安全CAN接收（ASIL-B车速信号直通）             │  │
  │  └─────────────────────────────────────────────────┘  │
  └──────────────────────────────────────────────────────┘

Lockstep MCU工作原理：
  1. MCU0 和 MCU1 同时执行完全相同的指令
  2. 两个核的输出在每个时钟周期进行比较
  3. 如果输出不一致 → 触发安全响应（复位/进入安全状态）
  4. 故障检测时间 < 1 个时钟周期（µs级）
```

### 5.1.3 ASIL分解（ASIL Decomposition）

对于无法单独达到高ASIL等级的功能，采用ASIL分解策略：

```
ASIL分解示例：车速显示（ASIL-B）

  原始需求：车速显示 ASIL-B

  分解方案：
  ┌──────────────────────┐  ┌──────────────────────┐
  │ 路径A：安全岛计算车速  │  │ 路径B：主处理器显示车速 │
  │ ASIL-B（独立）        │  │ QM（独立）             │
  └──────────┬───────────┘  └──────────┬────────────┘
             │                         │
             └─────────┬───────────────┘
                       │
               ┌───────▼───────┐
               │  安全监控单元  │  ◄─ 对比两路结果
               │ 不一致时报警   │
               └───────────────┘

  ASIL-B ──分解──► ASIL-B(A) + QM(B)（独立性前提下成立）
```

### 5.1.4 硬件功能安全措施

| 安全机制 | 应用位置 | 作用 |
|---------|---------|------|
| ECC（Error Correction Code） | L1/L2/L3 Cache、SRAM | 单比特纠错，双比特检错 |
| 奇偶校验 | 寄存器堆、总线 | 检测数据翻转 |
| Lockstep | 安全岛MCU | 双核比较，检测随机硬件故障 |
| CRC（Cyclic Redundancy Check） | 总线传输、显示帧 | 数据完整性验证 |
| 看门狗（Watchdog） | 安全岛、MCU | 检测软件死锁/CPU宕机 |
| 温度/电压监控 | PMU、热传感器 | 防止超温/欠压导致功能失效 |
| BIST（内建自测试） | CPU/GPU/NPU/内存 | 上电自检，检测制造缺陷 |
| 故障注入支持 | 硬件寄存器 | FMEDA测试，验证诊断覆盖率 |

### 5.2.2 硬件安全模块（HSM）

**HSM**（Hardware Security Module）是座舱SoC内置的安全加密处理单元：

```
HSM功能架构

  ┌──────────────────────────────────────────────┐
  │              HSM（硬件安全模块）                │
  │                                              │
  │  密钥管理                                     │
  │  ├── 硬件根密钥（HRoT/OTP Fuse存储）          │
  │  ├── 设备唯一密钥（DeviceID，出厂注入）        │
  │  ├── 会话密钥生成与销毁                        │
  │  └── 密钥层级（KEK→DEK，密钥加密密钥）        │
  │                                              │
  │  密码算法加速器                               │
  │  ├── 对称加密：AES-128/256（CBC/GCM/CCM）     │
  │  ├── 非对称加密：RSA-2048/4096, ECC P-256    │
  │  ├── 哈希：SHA-256/384/512                   │
  │  ├── MAC：HMAC-SHA256, CMAC-AES              │
  │  └── 随机数：TRNG（真随机数生成器）            │
  │                                              │
  │  安全存储                                     │
  │  ├── OTP（一次性可编程）：芯片序列号/根证书    │
  │  ├── 安全SRAM：运行时密钥（断电即清除）        │
  │  └── eFuse：安全启动配置                      │
  │                                              │
  │  安全服务                                     │
  │  ├── 数字签名验证（OTA包、固件）              │
  │  ├── TLS握手加速                              │
  │  └── 数字车钥匙认证（UWB+BLE）               │
  └──────────────────────────────────────────────┘

⚠️ HSM独立运行，主处理器无法直接访问密钥原文，只能调用安全服务API
```

### 5.2.3 安全启动（Secure Boot）

```
安全启动链（Chain of Trust）

  BootROM（芯片内固化，不可修改）
      │ 验证：BootLoader签名（使用OTP内根公钥）
      ▼
  BootLoader（Flash存储）
      │ 验证：OS Image签名
      ▼
  Hypervisor / TEE
      │ 验证：各VM镜像签名
      ▼
  Android / QNX / Linux VM
      │ 验证：应用包签名（APK/运行时）
      ▼
  应用层

每一级的验证过程：
  1. 读取待加载镜像的数字签名
  2. 使用上一级提供的公钥验证签名
  3. 验证通过 → 跳转执行
  4. 验证失败 → 拒绝启动 / 进入恢复模式

⚠️ 防回滚（Anti-Rollback）机制：
   通过OTP计数器防止降级安装旧版本固件
```

### 5.2.5 OTA安全更新机制

```
OTA（Over-The-Air）安全流程

  云端TSP平台
      │ HTTPS（TLS 1.3）
      ▼
  T-BOX（车联网盒）
      │ IPSec VPN / HTTPS
      ▼
  座舱域控以太网
      │
      ▼
  OTA客户端（运行在Android/Linux）
  ├── 1. 从云端下载更新包（加密+签名）
  ├── 2. 验证包的数字签名（调用HSM）
  ├── 3. 验证版本号（防回滚）
  ├── 4. 解密更新包（AES-256-GCM）
  ├── 5. 写入备份分区（A/B分区方案）
  ├── 6. 重启切换到新分区
  └── 7. 验证新固件完整性，失败则回滚到旧分区

A/B分区更新特点：
  ├── 后台下载，不中断当前使用
  ├── 更新失败自动回滚，零风险
  └── 支持差分更新（仅下载差异部分，节省流量）
```

## 5.3 功能安全与信息安全的协同

```
FuSa（功能安全）与 CySec（信息安全）的交叉领域

  共同关注：
  ├── 安全启动：防止恶意固件（CySec）& 防止错误固件（FuSa）
  ├── 安全通信：防篡改（CySec）& 防错误（FuSa E2E）
  └── 看门狗/监控：检测攻击导致的功能失效（CySec→FuSa）

  冲突点与解决：
  问题：信息安全加密增加计算延迟 → 可能影响实时安全功能
  解决：硬件加速（HSM）保证密码操作不影响安全关键路径

  问题：OTA更新可能引入功能安全风险
  解决：
  ├── OTA更新必须通过安全包验证（CySec）
  ├── 新固件必须通过FuSa自检（BIST）
  └── A/B分区确保可回滚（FuSa韧性）
```
